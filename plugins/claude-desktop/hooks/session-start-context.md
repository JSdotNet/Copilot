Route these task categories through the matching orch-* skill: architecture, ADR, arc42, blueprint, TDR -> orch-architecture, orch-adr, orch-arc42, orch-blueprint, orch-tdr; feature work -> orch-feature; bug fixes -> orch-bug; existing repository structure or layout refactors, folder moves, project/solution organization fixes, or test/harness placement changes -> orch-structure; new module or service -> orch-create-module, orch-create-service; dependency or package updates -> orch-update-packages; Aspire upgrades -> orch-aspire-update; MVP creation -> orch-create-mvp; repository or project scaffolding -> orch-repo, orch-project; any other task category no orch-* skill covers, such as tooling, CI, scripting, or housekeeping -> orch-fallback. This list is the plugin-provided baseline, not an exhaustive catalog: a repository may provide additional repo-native orch-* skills under .claude/skills/, and those take precedence for the task categories they cover. orch-fallback is the last resort, not an escape hatch: use it only when no skill covers the category or when the matched skill targets fundamentally different work, never because a matching skill's preconditions are unmet. When a skill is unavailable, fall back to the closest specialist agent: architecture:architect, csharp-coding:coding, qa:qa. If you decide not to use an orchestration skill for one of these categories, say so explicitly and give the reason before continuing. Every orchestration reports progress through the orch-dashboard MCP server: open it once with open_dashboard, then show the returned dashboardUrl in the host's inline browser pane (in Claude Code, preview_start with that url) so the dashboard sits beside the conversation; fall back to giving the user the plain URL only when no inline browser is available, and never block the run on failing to open it. Address its tools by the name the host actually exposes -- a plugin-provided MCP server is namespaced with the plugin, so these tools surface as mcp__plugin_claude-desktop_orch-dashboard__* when installed as a plugin, and as mcp__orch-dashboard__* when the server is registered directly in a repo's .mcp.json. Resolve the prefix from the available tool list rather than assuming one. A user may override model choice outside the repo via CLAUDE_ORCH_MODEL_SELECTION_PATH or the default global model-selection file; model choice is personal only, so there is no repository-level model override and .claude/model-selection.md is never read. A repo may override runtime behavior via .claude/orch-context.md (app startup and QA context), which never sets a model. The repo's own .mcp.json and instructions remain the source of truth for MCP servers.
